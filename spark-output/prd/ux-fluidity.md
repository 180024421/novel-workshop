# PRD — 大帅墨枢 · 日更流畅度版（UX Fluidity Release）

- **生成时间**：2026-09-22
- **数据源**：无上游 Skill 产出（standalone 模式）；证据来源为 2026-09-22 代码级操作走查（src/ 渲染层，121 文件 / 26.7k 行）+ 用户痛点确认（三组实锤全部命中）
- **完整度**：moderate —— Solution / Constraints / Release 有代码证据强支撑；Background / Value Prop 基于单人自用产品推断，无竞品走查输入

---

## Section 1 — Summary

大帅墨枢（Electron + React 19 桌面 AI 小说写作应用，v0.5.0）的本个版本不新增任何写作能力，只做一件事：**把「每天打开应用 → 写完一章 → 切下一章」这条日更主循环从 15 次点击 + 4 次切页 + 2 次弹窗，压成 2 次点击以内**，同时修掉三个正在伤害稿子的可靠性缺陷（换章丢尾段、Ctrl+Enter 失效、新生成章节不出现在侧栏）。给谁用：像作者本人这样一人驱动 AI 日更的独立网文作者——工具是他每天用 4 小时的生产线，不是偶尔打开的玩具。为什么是现在：0.5 已完成功能铺设（卷章/伏笔/合规/导出全链路 + 测试与 CI 门禁刚建立），此刻是偿还交互债、让功能真正被"用得起来"的唯一低成本窗口。成功长这样：作者连续 7 天日更期间，主循环零跳页、零丢字、零"请先去 XX 页"打断。

---

## Section 2 — Background & Problem

**问题（用户视角）**：
墨枢的功能都在，但每个功能各占一个页面，页面之间靠"请先去 XX"文案互相指路。写下一章时系统说"请先在右侧和 AI 聊聊构想"、"请先去细纲补本章"——明明上一秒刚让 AI 生成过细纲，它不认账，要我再切一页手动触发。共 **40+ 处「请先…」式人工串联**（证据：`useStudioGenerate.ts:145-154,426-433`、`ChapterTools.tsx:286-289`、`writePipeline.ts:214`、`StudioEditorPane.tsx:333,344`、`HealthPage.tsx:80,116,125`）。工具与资料页 16 个入口藏在折叠导航里，且**第二次启动起永久收起**（`AppLayout.tsx:106-112,255-262`），批量写这种日更刚需功能藏得最深。

**当前 workaround**：
作者按固定顺序人肉巡逻：设定页 → 总纲页 → 细纲页 → 正文页，每页跟 AI 聊一轮再点生成；生成一章要吞两次确认弹窗（重写 + 费用，`ChapterTools.tsx:290-296`）；想批量写十章得先去设置里看 serialPlan、再跳批量页手填"从第/到第"（`BatchPage.tsx:191-228`）。换章时最后打的字会静默丢失（`useAutoSave.ts:18-32` 防抖定时器在换章被 clear 且首帧跳过），只能靠备份列表手动找回——而备份只露 4 条（`ChapterTools.tsx:1380`）。

**为什么是现在**：
止血版（2026-09-20）刚修完并发生成串台、建立 CI 门禁，回归安全网第一次存在；0.5 功能面已收口，接下来若不做体验版，每次日更都在为交互缺陷持续付费。

**不解决什么（本 PRD 故意排除）**：
1. **AI 生成质量本身**（提示词工程、工艺规则扩充）——那是内容迭代线，与本版本解耦。
2. **前端性能重构与安全加固**（AppContext 全量重渲染、IPC 路径校验、授权协议防重放）——已入 backlog，见 Section 7 约束；本版本只允许为达成响应指标做**局部** memo 处理。

## Section 3 — Personas & User Segments

**Primary persona**

```
姓名：大帅（= 产品作者本人，dogfooding 用户）
身份：Windows 个人开发者 + 网文作者，一人同时扮演 PM / 设计师 / 工程师 / 用户
情境：每天固定时段开墨枢日更，一次 2-5 小时；同时挂 1-3 本书，习惯攒稿
JTBD：当坐下来要日更时，大帅想以最少的操作把「今天的章节」全部产出并落在稿上，
      从而把时间花在故事本身而不是工具巡逻上。
当前 workaround：人肉按页面顺序巡逻（设定→总纲→细纲→正文），手动重跑下游（摘要/钩子），
                丢字后翻备份列表拼稿。
痛点：「请先去XX」打断心流；弹窗多；批量入口藏太深；丢字让他不敢直接改正文。
```

**Secondary persona**：无独立买家——自用产品，作者即用户。**这为发布节奏去除了跨团队协调成本，也意味着所有验收标准必须可被作者一人执行。**

**这个产品不为谁做**：不为"偶尔写点东西的轻度用户"做向导式引导；本版本一切改动只为高频日更者压缩路径，低频质检/统计页允许变远。

## Section 4 — Goals & Success Metrics

**产品目标**：把日更主循环（打开应用 → 产出一章 → 进入下一章）从测量基线 **15 次点击 + 4 次切页 + 2 次弹窗** 压缩到 **≤ 2 次点击、0 次切页、0 次阻断弹窗**，且主循环零数据丢失。

**成功度量表**（单人产品，全部可用操作路径统计而非埋点）：

| 指标 | 度量什么用户行为 | 目标值 | 时间窗 |
| --- | --- | --- | --- |
| 主循环点击数 | 从侧栏点「下一章」到正文开始流出，经过的鼠标点击次数 | ≤ 2 | 发布即测 |
| 「请先…」阻断次数 | 写作循环中命中硬门槛文案、需跳页解除的次数 / 每章 | 0（缺料时**就地**补齐） | 发布即测 |
| 丢字事件 | 换章/关窗后对比内存内容与落盘文件，尾段丢失 | 0 次 / 每周 | 30 天 |
| 批量完成率 | 启动「写到第 N 章」队列后无需人工介入即完成的比例 | ≥ 90%（失败可单章重试不重置队列） | 30 天 |
| 章目录新鲜度 | 新生成章节出现在侧栏前的等待 | ≤ 1s 或无需重开卷 | 发布即测 |

**Anti-metric（反指标，明确不优化）**：
- **页面/功能区数量**：不做"更多入口"式改进；本版本目标是**减少**可见一级导航项，任何"为露出而加页"的方案一票否决。
- **设置项暴露度**：serialPlan 等参数不搬到正文页增加存在感，改为被队列隐式消费。

**关键假设**：如果"操作不方便"的根因是**页面割裂 + 人工串联**，而非功能缺失——该假设已被 2026-09-22 用户确认（三组实锤全选中、未选"另有痛点"），风险显著降低，但仍以 S1 发布后一周的跳页次数作为最终验证。

## Section 5 — Value Proposition

**对主用户**：

> 大帅终于可以"打开墨枢 → 点继续 → 今天的稿子自己长出来"，而不必在 5 个页面之间巡逻并替工具记住每一步的前置条件，因为本版本把"阶段间硬门槛"改成了"缺料就地补"，把"逐章手动"改成了"队列自动续"。

**竞争差异化**（对照泛用 AI 写作工具与同类桌面写作软件，定性判断）：
- 泛用工具（网页端 ChatGPT/Kimi 类）没有卷/细纲/伏笔台账的**持久化上下文**，写长篇必然漂移——墨枢 0.5 已解决，但操作成本反而更高；本版本要证明"有结构的工具也能比聊天框顺手"。
- 同类写作软件（Scrivener、Effical 等）省的是"写作管理"成本，不省"AI 流水线串联"成本——墨枢的空白点正是**让 AI 产线自己转**：自动续章、就地补料、一键重跑下游，这三件事竞品和聊天框都不做。

## Section 6 — Solution & Feature Scope

> 8 个 Story，按 priority 降序。验收标准均可由作者单人执行（点几下、看什么、对比什么）。"已生成设计资产"列当前为待生成，但每项附**现有代码锚点**（文件:行号），coding agent 可从锚点直接起步。

### S3（P0，先发）换章不丢字、Ctrl+Enter 随处可按、新章即时出现在侧栏

**Persona**：大帅 · **优先级**：P0 · **关键假设标记**：无（纯缺陷修复）

**功能描述**：
这三条不是"优化"，是正在损坏用户稿子的 bug。自动保存 700ms 防抖在换章时被 clear 且首帧跳过，最后 700ms 内打的字静默蒸发；默认编辑器是 CodeMirror（contenteditable），而 Ctrl+Enter 处理器只认 `TEXTAREA` 标签，正文页写作的核心快捷键根本按不动；侧栏章目录只在 volumeId 变化时重算，刚生成的下一章不出现，看起来像"没写出来"。

**In Scope**：
- 换章 / 关窗 / 切路由前强制 flush 未落盘的编辑内容（`src/studio/useAutoSave.ts:18-32`、`useStudioDocument.ts:264`）
- Ctrl+Enter 改为不依赖 target 标签：焦点在 CodeMirror 内时照常触发"生成/继续"（`AppLayout.tsx:366`；锚点 `StudioCodeEditor.tsx:102`）
- 章节生成完成后章目录事件化刷新（不重开卷）（`AppLayout.tsx:178-207`）
- Diff 完成提示语与自动保存自相矛盾的文案清理（`ChapterTools.tsx:1413`「记得 Ctrl+S」）

**Out of Scope**：应用级 undo/redo 系统（成本大，用"永不丢字"替代达成安全感）；备份面板改造（仅把列表露出从 4 条放宽，属顺手项）。

**验收标准（Given / When / Then）**：
- Given 正文页刚打完几个字（<700ms），When 立即点击侧栏另一章，Then 旧章文件内容包含刚打的字，落盘时间戳更新。
- Given 焦点在 CodeMirror 编辑器中，When 按 Ctrl+Enter，Then 触发与按钮等价的"生成本章"动作；边缘：焦点在设置页输入框时行为不变。
- Given AI 刚流式生成完一章，When 流结束 ≤1s，Then 侧栏当前卷出现该章且可点击；边缘：生成中途取消，该章以草稿态出现而非消失。
- 空状态：新建项目尚无任何章时，侧栏不报错、正文页显示统一 EmptyGuide。

**设计触点**：涉及屏：StudioPage 正文编辑器、AppLayout 侧栏章目录；涉及组件：`useAutoSave`、`StudioCodeEditor`、`AppLayout` nav；涉及状态：保存中 / 已保存 / flush 强制保存。

**关联页面**：`/studio/*`、`/`（章目录）。

**已生成的设计资产**：待生成（无视觉稿需求，行为修复为主）。代码锚点：`src/studio/useAutoSave.ts`、`src/hooks/useStudioDocument.ts`、`src/pages/AppLayout.tsx`、`src/components/StudioCodeEditor.tsx`。

### S1（P0）拆掉写作循环的硬门槛：缺料就地补，支持"从上级一键直生"

**Persona**：大帅 · **优先级**：P0 · **关键假设标记**：⭐（验证"割裂是根因"假设的核心 Story）

**功能描述**：
idea/outline/beats 三页目前强制"先在右侧和 AI 聊天"才允许生成——即使用户根本不想聊。正文页遇到缺细纲时甩一句"· 请先去细纲补本章"加跳页链接，把一次点击能完成的事变成四次切页。改成：每页的生成按钮在被点击时若检测到前置物料缺失，**就地**（弹内联面板/自动展开右栏对话）引导补齐或直接"从上级一键直生"，全程不离开当前页。QuickStartPage 的流水线逻辑（种子→设定→总纲→细纲→首章，`QuickStartPage.tsx:84-174`）就是现成范本，抽出来复用。

**In Scope**：
- 移除三处硬门槛文案，替换为"就地补齐"交互（锚点：`useStudioGenerate.ts:145-154,426-433`、`ChapterTools.tsx:286-289`、`writePipeline.ts:214`）
- "从上级直生"按钮：idea 页直生总纲 / 总纲页直生本卷细纲 / 正文页缺细纲时内联生成（复用 QuickStart 流水线函数）
- 跳页链接降级为辅助入口保留（老用户习惯）

**Out of Scope**：重构 QuickStartPage 视觉；把两条平行开书路径（首页"开始写新书" vs 一句话开书）合并——仅加互链，合并放 P2。

**验收标准**：
- Given 本章无细纲，When 在正文页点"生成本章"，Then 出现内联补细纲流程且补齐后自动继续生成正文，全程不跳页。
- Given 总纲页，When 点"直生本卷细纲"，Then 逐章生成细纲并展示进度，完成提示可一键跳正文。
- Given 全新构想页未聊过天，When 直点"生成构想稿"，Then 不再出现"请先聊"阻断，以输入框当前内容（含空）为种子生成。
- 边缘：直生中途取消，已生成的部分物料保留且状态标记为"未完成"。

**设计触点**：屏：StudioPage 三阶段页 + 正文页；组件：内联补齐面板（新）、生成按钮态；状态：缺料→就地补→继续。

**已生成的设计资产**：待生成。代码锚点：`src/pages/QuickStartPage.tsx`（流水线参考）、`src/hooks/useStudioGenerate.ts`、`src/components/ChapterTools.tsx`。

### S2（P0）日更自动续章：正文页"写完自动切下一章" + 队列驱动批量

**Persona**：大帅 · **优先级**：P0

**功能描述**：
全库无任何 autoNext 机制（走查确认），批量写入口藏在折叠导航且要手填"从第/到第"（`BatchPage.tsx:191-228`），而 serialPlan 只在设置里编辑（`SettingsPage.tsx:771-810`）、不驱动任何执行。改成正文页就地一个"写到第 N 章"开关：开启后每章生成完成即自动进入下一章队列，队列消费 serialPlan 决定日更目标章数；失败单章可重试，不重置整个队列。

**In Scope**：
- 正文页生成区新增"自动续章"开关 + 目标章数（默认取 serialPlan）（锚点：`StudioEditorPane.tsx:355-361` 现手动"下一章"）
- 简单队列执行器：复用 `writePipeline` 单章流程，逐章执行、逐章落状态，UI 露出"第 3/10 章生成中·失败 1（可重试）"
- 弹窗合并：重写确认保留，费用确认并入主按钮（点击即含授权额度预检，不足时才弹窗）（锚点：`ChapterTools.tsx:290-296`）

**Out of Scope**：夜间挂机无人值守跑全卷（涉及失败重试策略复杂度，P2）；跨书队列。

**验收标准**：
- Given 开关开启且目标 +5 章，When 当前章生成完成，Then ≤3s 自动开始下一章，侧栏与编辑器同步切换，无需任何点击。
- Given 队列中第 2 章网络失败，When 队列运行，Then 其余章不受影响，失败章红标并提供单章重试。
- Given 有授权额度，When 点"生成本章"，Then 不再出现独立费用弹窗；边缘：额度不足时仍必须弹一次明确费用的确认。
- 空状态：serialPlan 未设置时开关默认目标 = 1 并在 tooltip 说明。

**设计触点**：屏：正文页生成区、侧栏章目录（队列态角标）；组件：队列进度条（新）、自动续章开关；状态：排队中 / 生成中 / 失败可重试 / 全部完成。

**已生成的设计资产**：待生成。代码锚点：`src/lib/writePipeline.ts`、`src/hooks/useStudioGenerate.ts`、`src/lib/serialPlan` 相关设置段。

### S5（P1）导航重组：高频浮出、低频收纳、折叠不再"见过即永久收起"

### S6（P1）指引死路清障：摘要/钩子"一键补齐全部"

**Persona**：大帅 · **优先级**：P1

**功能描述**：
一致性检查与健康分都要求"先补齐章摘要"（`consistencyCheck.ts:85`、`HealthPage.tsx:80`），但摘要只在写章时生成、摘要页只能手改文本（`SummariesPage.tsx:102-113`）；StatusPage 写着"写完章后点抽钩子"却没有该按钮（`:384`），抽钩子实际藏在 ChapterTools 更多菜单（`ChapterTools.tsx:1151-1158`）。健康分把你指到一条死路。给"缺什么"的每一处提示配一个真正可点的补齐动作。

**In Scope**：
- 摘要页/健康分页/一致性页：新增"补齐缺失摘要"按钮，队列式对已有正文、无摘要的章节批量生成（复用 S2 执行器）
- StatusPage 文案处补上真实"抽钩子"按钮；重试路径从"跳进度页"改为原地按钮（`HealthPage.tsx:396-404`、`StatusPage.tsx:339-350`）
- grep 清理：所有"请先/前往"文案，凡目标动作可就地执行的改为就地执行

## Section 7 — Constraints & Risks

**技术约束**：
1. 单人开发 + coding agent 协作，所有改动必须过既有 CI 门禁（tsc -b + oxlint + 104 测试，2026-09-20 建立）。
2. **前端性能重构不在本版**：AppContext 22 字段全量重渲染、67-props StudioEditorPane、0 处 React.memo 是已知债（已记录 backlog）。S2 队列和 S1 内联面板**不得新增**跨页全局 state；允许对改动涉及的组件做局部 memo，禁止顺手拆 Context（会把本版拖成重构版）。
3. 安全加固（IPC 路径校验、safeStorage、授权协议防重放）延后——本 PRD 的自动续章会放大调用频率，**要求 S2 上线前至少完成 usage 计费的读-改-写并发丢更新修复**（backlog 已录）。
4. Electron 层改动最小化：本版原则上只动 src/ 渲染层，唯一例外是 autosave flush 若需主进程配合（fs:writeText 已有）。

**设计约束**：不新增一级导航页面；不引入新 UI 库；所有新交互（内联补齐、队列）必须在现有暗色体系内完成。

**数据 & 隐私**：不涉及新增个人数据；改动核心触及**用户稿子的写入路径**（autosave / 队列写章），属最高风险等级——任何丢字回归都是不可豁免的 P0。

**关键风险表**：

| 风险 | 可能性 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| autosave flush 改动引入新的丢字场景 | M | **High（毁稿）** | 先写"换章丢尾"复现测试（vitest，模拟 700ms 内切章），红→绿再合并；发布前用 `docs/e2e-smoke.md` 增加手测项 |

## Section 8 — Release Approach

**推荐顺序**：S3（数据可靠性，任何版本都该先发）→ S1（验证关键假设，⭐ 先发它才能确认"割裂是根因"）→ S2（自动续章，依赖 S3 的 autosave 修复 + S1 的就地补料）→ S7 → S5 → S6 → S4/S8（P2 池）。

**MVP 定义**：S3 + S1 + S2。三件事做完即可宣称"日更流版本"：不丢字、不跳页、自动续章——恰好覆盖用户确认的三组痛点各一个最大项。

**Phase 2**：S4 设置搜索、S8 开书合并 + 命令面板、无人值守夜跑。理由：P2 项都依赖 MVP 队列执行器的稳定性数据。

**上线考虑**：
- 单人产品无需灰度，但 S3 合并后先自用 2 天日更再发 S1/S2（作者即用户 = 天然 dogfood 通道）。
- 发布节奏沿用现状：每完成一个 Story 一个 commit + CI 绿，合并打 tag（补上 backlog 里"无 tag"债）。
- 上线后头 2 周监测：丢字事件数（应为 0）、队列人工介入率、`crash.log` 有无新增写盘异常。
